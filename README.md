# Zonify — บัญชีผู้ใช้ ผังตลาด ร้านค้า และการจอง

เชื่อม Next.js + Express + MongoDB สำหรับบัญชีผู้ใช้ ผังตลาด ค้นหาร้านค้า ระบบผู้จัดการ จองรายวัน/พักล็อก ชำระด้วย PromptPay พร้อมตรวจสลิป ข่าวประชาสัมพันธ์ Dashboard และรายงาน มี seed ข้อมูลตัวอย่างให้ทดลอง

## เริ่มใช้งานในเครื่อง

ใช้ Node.js 22 ขึ้นไป, pnpm ตาม package.json และ MongoDB 8 (ติดตั้งเองหรือใช้ Docker Desktop) เปิด Docker Desktop ก่อนใช้คำสั่ง Docker ด้านล่าง

1. ติดตั้ง dependencies และคัดลอกไฟล์ตั้งค่า **เมื่อยังไม่มีไฟล์ปลายทาง**:

   ```powershell
   cd D:\zonify\backend
   pnpm install --frozen-lockfile
   if (!(Test-Path .env)) { Copy-Item .env.example .env }
   cd ..\frontend
   pnpm install --frozen-lockfile
   if (!(Test-Path .env.local)) { Copy-Item .env.example .env.local }
   ```

2. ตั้งค่า backend/.env:
   - BACKEND_PORT=4000
   - MONGO_URI=mongodb://127.0.0.1:27017/zonify
   - APP_ORIGIN=http://localhost:3000
   - JWT_SECRET เป็นค่าสุ่มอย่างน้อย 32 ตัวอักษร สร้างด้วย `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`
   - กำหนด SEED_CUSTOMER_PASSWORD, SEED_MANAGER_PASSWORD, SEED_OWNER_PASSWORD ด้วยค่าที่เลือกเอง ความยาว 8–72 UTF-8 ไบต์ ไม่ต้องตั้ง seed หากไม่สร้างบัญชีตัวอย่าง
   - อีเมล seed เริ่มต้น: customer@zonify.test, manager@zonify.test, owner@zonify.test เปลี่ยนได้ด้วย SEED_*_EMAIL และแต่ละบทบาทต้องใช้อีเมลต่างกัน

3. เริ่มฐานข้อมูล แล้วเตรียมข้อมูลก่อนเปิด API:

   ```powershell
   cd D:\zonify\backend
   docker compose up -d mongodb
   pnpm migrate:auth
   pnpm seed:auth
   pnpm seed:catalog
   pnpm dev
   ```

   คำสั่ง seed เป็นตัวเลือกและไม่เขียนทับบัญชีที่มีอยู่ หากใช้ MongoDB ที่ติดตั้งเองให้ข้ามคำสั่ง Docker

4. เปิด terminal อีกหน้าต่าง:

   ```powershell
   cd D:\zonify\frontend
   pnpm dev
   ```

เปิด http://localhost:3000 (ใช้ localhost ให้ตรง APP_ORIGIN ไม่สลับเป็น 127.0.0.1) API อยู่ที่ http://localhost:4000 และเอกสารอยู่ที่ http://localhost:4000/api-docs

frontend/.env.local ใช้ BACKEND_URL=http://localhost:4000 หากเปลี่ยนค่านี้ให้ restart dev server หรือ build frontend ใหม่

## ข้อมูลเดิมและ migration

หยุด backend และสำรองฐานข้อมูลก่อนรัน `pnpm migrate:auth` กับข้อมูลที่มีอยู่ คำสั่งตรวจอีเมลซ้ำหลัง trim/lowercase และบทบาทที่ไม่ถูกต้องก่อนเริ่มเขียน หากพบปัญหาจะรายงาน ID และหยุดโดยไม่แก้หรือลบบัญชี ให้ผู้ดูแลแก้ข้อมูลแล้วรันใหม่

เมื่อผ่านการตรวจ จะ normalize อีเมล เติม customer ให้บัญชีที่ไม่มี role และสร้าง unique email index รันซ้ำได้ รหัสผ่านเดิมไม่ถูกเปลี่ยน บัญชีที่มีรหัสผ่านเดิมสั้นกว่า 8 ไบต์ยังล็อกอินได้ แต่การสมัครและตั้งรหัสผ่านใหม่ใช้ข้อกำหนดใหม่

API จะไม่เริ่มหากข้อมูลยังต้อง migrate หรือไม่สามารถสร้าง unique index ได้ ป้องกันการสมัครอีเมลซ้ำพร้อมกันด้วย index ในฐานข้อมูล

## คู่มือผู้ใช้

- สมัครที่ /register ด้วยชื่อ อีเมล รหัสผ่านและยืนยันรหัสผ่าน จากนั้นเข้าสู่ระบบที่ /login
- /profile แก้ชื่อและเบอร์โทรได้ อีเมลและบทบาทแก้จากหน้าจอไม่ได้
- เปลี่ยนรหัสผ่านด้วยรหัสผ่านเดิม ทุกอุปกรณ์จะออกจากระบบ และต้องล็อกอินใหม่
- ปุ่มออกจากระบบอยู่ที่หัวเว็บ ยกเลิกเฉพาะ session ของอุปกรณ์นั้น
- session มีอายุ 1 ชั่วโมง ไม่มีการต่ออายุอัตโนมัติหรือบริการลืมรหัสผ่าน/ยืนยันอีเมล

## สิทธิ์และ API

| เส้นทาง | สิทธิ์ / พฤติกรรม |
| --- | --- |
| POST /api/users | สมัครเป็น customer เท่านั้น ส่ง role มาไม่ได้ |
| POST /api/users/login | ส่งกลับ User พร้อม cookie ไม่ส่ง token ใน JSON |
| POST /api/users/logout | ยกเลิก session ปัจจุบันและล้าง cookie เรียกซ้ำได้ |
| GET /api/users/me | ข้อมูลตนเองหลังล็อกอิน |
| PATCH /api/users/me | แก้ name และ phone ของตนเอง |
| PATCH /api/users/me/password | ส่ง currentPassword และ password ใหม่ แล้วเพิกถอนทุก session |
| GET /api/users | manager / owner อ่านรายชื่อ |
| GET /api/users/:id | manager / owner อ่านข้อมูลรายบุคคล |
| DELETE /api/users/:id | owner ลบบัญชีอื่น ห้ามลบตนเอง |

ทุก User response มีเฉพาะ id, name, email, phone, role การตรวจสิทธิ์อ่านบทบาทล่าสุดจากฐานข้อมูล หน้า /admin สำหรับ manager/owner ไม่มี API เปลี่ยนบทบาท ใช้ seed สร้างบัญชีทั้ง 3 บทบาทสำหรับทดสอบ

คำขอที่เปลี่ยนข้อมูลต้องส่ง Origin ตรง APP_ORIGIN รวมถึง Postman/curl ส่วน browser ใช้ /api ผ่าน Next proxy อัตโนมัติ Cookie เป็น HttpOnly, SameSite=Lax และ Secure เมื่อ APP_ORIGIN เป็น HTTPS การเปลี่ยนรูปแบบจาก bearer token เป็น cookie เป็น breaking change สำหรับ client เก่า

จำกัดสมัคร 10 ครั้ง/ชั่วโมง และล็อกอิน/เปลี่ยนรหัสผ่านรวม 20 ครั้ง/15 นาทีต่อ IP ที่ backend เห็น ในการรันเครื่องเดียวคำขอผ่าน Next proxy ใช้งบเดียวกันและไม่เชื่อ X-Forwarded-For จาก client ตัวนับอยู่ในหน่วยความจำ backend; การใช้งานหลาย instance ต้องเพิ่ม shared store และกำหนด trusted proxy ก่อนใช้งานจริง

## ทดสอบและ build

```powershell
cd D:\zonify\backend
pnpm test
pnpm build
cd ..\frontend
pnpm lint
pnpm build
```

API integration tests ใช้ MongoDB ชั่วคราวแยกจาก MONGO_URI ของผู้ใช้และลบทิ้งเมื่อจบ ไม่ต้องเปิด Docker การรันครั้งแรกดาวน์โหลด MongoDB binary สำหรับระบบปฏิบัติการ (Windows ประมาณ 780 MB) และใช้ cache ในครั้งถัดไป ไม่มีการดาวน์โหลดในขั้น pnpm install

ทดสอบผ่าน browser: สมัคร → ล็อกอิน → รีเฟรช → แก้โปรไฟล์ → เปลี่ยนรหัสผ่าน → ล็อกอินใหม่ → ออกจากระบบ ตรวจหน้า desktop/mobile และลองส่งแบบฟอร์มว่างด้วยคีย์บอร์ด

## Docker backend (ทางเลือก)

หลังเตรียม .env และ migration แล้ว ใช้ `docker compose up -d --build backend` ใน backend/ เพื่อเปิด API พร้อม MongoDB โดย frontend ยังรันแยกตามข้างต้น พอร์ตที่เปิดใช้เฉพาะ loopback ของเครื่อง ไม่มีการ deploy ภายนอก

## ผังตลาดและค้นหาร้านค้า (rs003–rs004)

- หน้าแรกเลือกตลาดและวันที่เพื่อดูสถานะล็อก: ว่าง จองแล้ว พักล็อก และปิดใช้งาน
- กดทุกล็อกเพื่อดูขนาด ค่าเช่ารายวัน และรายละเอียด มีปุ่มขยาย/ย่อและเลื่อนผังได้บนมือถือ
- ดึงสถานะใหม่ทุก 15 วินาทีเมื่อหน้าเว็บมองเห็นอยู่ และเมื่อกลับมาโฟกัส มีปุ่มรีเฟรชทันที หากโหลดล้มเหลวจะซ่อนผังเดิมพร้อมปุ่มลองใหม่
- ค้นหาร้านด้วยชื่อหรือคำในคำอธิบาย กรองตลาดและหมวดหมู่ร่วมกันได้ แสดงครั้งละ 6 ร้าน พร้อมแบ่งหน้าและล้างตัวกรอง
- /shops/:id แสดงรายละเอียดร้าน หมวดหมู่ เวลาเปิด และตำแหน่งล็อก กดดูตำแหน่งบนผังเพื่อเปิดตลาดพร้อมเลือกล็อกนั้นได้
- วันที่ทั้งหมดใช้ปฏิทิน Asia/Bangkok การเลือกวันที่ต่างกันอ่านสถานะคนละชุด ล็อกที่ปิดใช้งานคงสถานะปิด ส่วนพักล็อกที่หมดอายุแสดงว่างโดยไม่ต้องรอการล้างข้อมูล

`pnpm seed:catalog` สร้างตลาด 3 แห่ง ล็อก 66 ล็อก หมวดหมู่ 4 หมวด และร้าน 13 ร้าน พร้อมสถานะตัวอย่างของวันปัจจุบัน รันซ้ำไม่เขียนทับเอกสารที่มีอยู่ หากต้องการวันเฉพาะให้กำหนด SEED_DATE=YYYY-MM-DD ก่อนรัน ตัวอย่างสถานะพักล็อกหมดอายุเมื่อสิ้นวันนั้น

ข้อมูล seed เป็นข้อมูลสมมติสำหรับทดลอง ไม่ใช่การจองหรือข้อมูลร้านจริง ถ้าไม่รัน seed ฐานข้อมูลว่างจะแสดงข้อความว่ายังไม่มีข้อมูลอย่างชัดเจน ผู้จัดการแก้ข้อมูลผ่าน /admin ได้ ลูกค้าพักล็อกและจองผ่านหน้าเว็บได้ รัน seed ก่อนเปิด API เพื่อไม่ให้ข้อมูลตัวอย่างชนกับการจองที่กำลังเกิดขึ้น

| Public API | พฤติกรรม |
| --- | --- |
| GET /api/markets | ตลาดที่เปิดแสดงพร้อมราคาต่ำสุดจากล็อกที่เปิดใช้งาน |
| GET /api/categories | หมวดหมู่ที่เปิดแสดง |
| GET /api/markets/:id/floor-plan?date=YYYY-MM-DD | ตำแหน่ง/ขนาด/ราคา/สถานะล็อกและยอดรวมตามวัน ค่าเริ่มต้นเป็นวันนี้ในไทย |
| GET /api/shops?q=...&market=...&category=...&page=1&limit=12 | ค้นหาคำแบบข้อความตรง ไม่ตีความเป็น regex และใช้ตัวกรองร่วมกัน |
| GET /api/shops/:id | รายละเอียดร้านและตำแหน่งล็อกที่ตรวจว่าอยู่ในตลาดเดียวกัน |

ทุก endpoint ข้างต้นเปิดอ่านโดยไม่ต้องล็อกอินและส่ง Cache-Control: no-store ร้านที่ปิดแสดงหรืออยู่ในตลาด/หมวดหมู่ที่ปิดแสดงไม่ปรากฏในผลค้นหา รายละเอียดที่ไม่มีอยู่ตอบ 404; วันที่และ query ที่ผิดรูปแบบตอบ 400

ชุดทดสอบ catalog เพิ่มการตรวจผังต่างตลาด สถานะต่างวัน การหมดอายุของพักล็อก การค้นหาภาษาไทย ตัวกรองร่วม pagination การปิดแสดงข้อมูล และ seed ที่ไม่เขียนทับข้อมูลเดิม โดยใช้ฐานข้อมูลทดสอบแยก


## หน้าผู้จัดการ (rs009–rs011, rs015)

เข้าสู่ระบบด้วย manager หรือ owner แล้วเปิด /admin (เมนู “จัดการตลาด”):
- ตลาด: ชื่อ ที่ตั้ง คำอธิบาย ภาพ จุดสังเกต ชื่อทางเข้า ลำดับ และเปิด/ปิดแสดง
- หมวดหมู่: ชื่อ ลำดับ และเปิด/ปิดแสดง
- โซน: เลือกตลาด ชื่อ คำอธิบาย ลำดับ และเปิด/ปิดใช้งาน
- ล็อก: ตลาด โซน รหัส ชื่อแถว ตำแหน่งแถว/คอลัมน์ ขนาด ราคา และเปิด/ปิดใช้งาน
- ร้านค้า: ตลาด หมวดหมู่ ล็อก ชื่อ คำอธิบาย เวลาเปิด และเปิด/ปิดแสดง
- จัดผังล็อก: เลือกตลาดและกดล็อกบนผัง แก้ตำแหน่ง ขนาด โซน และราคา แล้วบันทึก การเพิ่มล็อกทำจากแท็บล็อก
- ผู้ใช้: ค้นหาชื่อ/อีเมล ดูบทบาทและเบอร์โทร เจ้าของลบบัญชีอื่นได้แต่ลบตนเองไม่ได้ ไม่มีหน้าหรือ API เปลี่ยนบทบาท

“ปิดใช้งาน” ข้อมูลหลักไม่ลบเอกสารหรือการอ้างอิง เปิดกลับจากแบบฟอร์มแก้ไขได้ ปิดโซนทำให้ล็อกในโซนนั้นแสดงปิดใช้งาน ตลาด/หมวดหมู่/ร้านที่ปิดแสดงไม่ปรากฏต่อผู้เข้าชม ล็อกที่ปิดยังเห็นบนผังพร้อมสถานะปิด

รหัสเอกสารและตลาดของโซน/ล็อก/ร้านเปลี่ยนไม่ได้หลังสร้าง รหัสล็อกและตำแหน่งแถว/คอลัมน์ต้องไม่ซ้ำภายในตลาด โซนและล็อกของร้านต้องอยู่ในตลาดเดียวกัน API ใช้ version ป้องกันการบันทึกทับข้อมูลที่ผู้จัดการคนอื่นเพิ่งแก้ (409 ให้โหลดรายการใหม่ก่อนแก้อีกครั้ง)

| Admin API | พฤติกรรม |
| --- | --- |
| GET /api/admin/references | ตลาด หมวดหมู่ โซน ล็อก ร้านค้า รวมข้อมูลที่ปิดใช้งาน |
| GET /api/admin/{kind}?q=...&market=...&page=1&limit=12 | ค้นหาชื่อ/รหัส แบ่งหน้า และกรองตลาดสำหรับ zones/stalls/shops/advertisements |
| POST /api/admin/{kind} | เพิ่มข้อมูล สร้าง id อัตโนมัติหากไม่ส่ง |
| PATCH /api/admin/{kind}/:id | แก้ข้อมูล ต้องส่ง version ล่าสุด |
| DELETE /api/admin/{kind}/:id | ปิดใช้งาน ต้องส่ง JSON { version } คืนข้อมูลหลังปิด |

kind คือ markets, categories, zones, stalls, shops หรือ advertisements ทุก endpoint ต้องเป็น manager/owner คำขอเปลี่ยนข้อมูลต้องมี Origin ตรง APP_ORIGIN ดูรายละเอียด fields และ error codes ใน Swagger

## ข่าวประชาสัมพันธ์ Dashboard และรายงาน (Phase 5)

ผู้จัดการ/เจ้าของใช้ /admin → **โฆษณา** เพิ่มชื่อ ข้อความ ตลาด ร้านค้าที่เกี่ยวข้อง (ไม่บังคับ) ภาพจากชุดภาพเดิม ลำดับ วันที่เริ่มและวันสุดท้ายที่แสดง หน้าแรกแสดงเฉพาะรายการที่เปิดใช้งานและอยู่ในช่วงวันที่ตาม Asia/Bangkok รวมวันแรก/วันสุดท้าย หากตลาดหรือร้าน/หมวดหมู่ปลายทางปิดแสดง ข่าวนั้นจะไม่แสดงด้วย ลิงก์สร้างจากข้อมูลตลาด/ร้านภายในระบบ ไม่มีช่องใส่ URL ภายนอก การปิดใช้งานเก็บประวัติไว้และเปิดกลับจากแบบฟอร์มได้

สร้างข่าวสมมติสามตลาดเพื่อทดลองด้วย `pnpm seed:ads` ใน backend หลัง seed:catalog คำสั่งไม่เขียนทับข้อความ วันแสดง หรือสถานะของข่าวที่มีอยู่แล้ว ตั้ง SEED_DATE=YYYY-MM-DD ได้สำหรับข้อมูลทดลอง

เมนู **Dashboard** แสดงตลาด/ร้านที่เปิดแสดง ผังและสถานะการจองของวันที่เลือก พร้อมยอดบันทึกรับ/คืนเงินวันที่เลือก อัปเดตทุก 20 วินาที ยอดรายการที่รอชำระและราคาการจองยังไม่ถือเป็นรายรับ

เมนู **รายงาน** เลือกช่วงวัน ตลาด และกลุ่มรายวัน/รายเดือน แล้วกดแสดงรายงาน ดาวน์โหลด CSV ได้ตามตัวกรองที่แสดง:

- ผู้จัดการ/เจ้าของอ่านรายงานการจองตาม **วันที่จอง** แยกตลาดและสถานะ รวมประวัติยกเลิก/หมดอายุ ยอดค่าเช่าใช้ราคาที่บันทึกตอนจอง
- เฉพาะเจ้าของอ่านรายงานรับ/คืนเงินตาม **วันที่ผู้จัดการบันทึกรับเงินหรือคืนเงิน** ตามเวลาไทย ไม่ใช้วันที่จองหรือวันที่บนสลิป รายรับที่ยกเลิกภายหลังยังอยู่ในวันที่รับ ส่วนคืนเงินอยู่ในวันที่บันทึกคืนจริง ยอดสุทธิของบางวันอาจติดลบ
- “รอคืนเงินทั้งหมด” คือภาระคืนเงินปัจจุบันของตลาดที่เลือกจากทุกวันที่ ไม่ถือว่าคืนแล้วและไม่หักจากยอดสุทธิในช่วงรายงาน
- ช่วงรายงานรวมวันแรกและวันสุดท้ายได้ไม่เกิน 366 วัน CSV เป็น UTF-8 พร้อม BOM สำหรับภาษาไทย และป้องกันข้อความชื่อที่เริ่มเหมือนสูตร Excel รายงานสรุปไม่ส่งข้อมูลติดต่อลูกค้าหรือภาพสลิป

| API | สิทธิ์ / พฤติกรรม |
| --- | --- |
| GET /api/advertisements | สาธารณะ ข่าวที่ควรแสดงวันนี้ |
| GET /api/admin/dashboard?date=YYYY-MM-DD&market=... | manager/owner ภาพรวมวันและตลาดที่เลือก |
| GET /api/admin/reports/bookings?from=...&to=...&market=...&group=day | manager/owner รายงานการจอง; group เป็น day หรือ month |
| GET /api/admin/reports/bookings/export | manager/owner CSV ด้วย query เดียวกับรายงาน |
| GET /api/owner/reports/revenue?from=...&to=...&market=...&group=day | owner รายงานบันทึกรับ/คืนเงิน |
| GET /api/owner/reports/revenue/export | owner CSV ด้วย query เดียวกับรายงาน |

Dashboard/รายงานต้องมี session และตอบ private/no-store วันที่ผิดจริง เช่น 2026-02-30 หรือ query ที่ไม่รองรับตอบ 400 ลูกค้าไม่ได้รับสิทธิ์เหล่านี้ และ manager เรียกรายงานเจ้าของโดยตรงได้รับ 403

## MongoDB ถาวรโดยไม่ใช้ Docker (Windows)

ทางเลือกสำหรับเครื่องที่มี mongod.exe หรือ binary cache จากการรัน API tests:
```powershell
cd D:\zonify
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/setup-local.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/mongodb.ps1 start
cd backend
pnpm migrate:auth
pnpm seed:auth
pnpm seed:catalog
pnpm dev
```

setup-local.ps1 สร้าง .env เฉพาะเมื่อยังไม่มี พร้อมรหัสผ่าน seed และ JWT แบบสุ่ม อ่านรหัสผ่านจาก backend/.env สำหรับล็อกอินแต่ละบทบาท และห้าม commit ไฟล์นี้ Frontend เปิดอีก terminal ด้วย pnpm dev ใน frontend

mongodb.ps1 ใช้ MONGOD_PATH, mongod ใน PATH หรือ binary cache ตามลำดับ เก็บข้อมูลใน D:\zonify\.data\mongodb (Git ignore) เปิดเฉพาะ 127.0.0.1:27017 หากพอร์ตมีบริการอื่นจะหยุดและให้เลือกใช้บริการนั้นเอง ไม่เปลี่ยนฐานข้อมูลของบริการอื่น

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/mongodb.ps1 status
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/mongodb.ps1 stop
```

stop หยุดเฉพาะ process MongoDB ที่ใช้ data directory ของโปรเจกต์นี้ ไม่ลบข้อมูล เปิด start อีกครั้งเพื่อใช้ข้อมูลเดิม อย่าเปิด native MongoDB และ Docker MongoDB ที่พอร์ต 27017 พร้อมกัน

ติดตามขอบเขตที่เหลือใน [docs/PHASES.md](docs/PHASES.md) และผลทดสอบที่ทำจริงใน [docs/TESTING.md](docs/TESTING.md)

## จองรายวันและพักล็อก (Phase 3)

- เลือกตลาด วันที่ และล็อกว่างบนหน้าแรก แล้วกด **พักล็อกนี้ 10 นาที** หากยังไม่ได้เข้าสู่ระบบ หน้าเข้าสู่ระบบ/สมัครสมาชิกจะพากลับมาที่ล็อกและวันที่เลือก
- แต่ละรายการจองได้หนึ่งล็อกต่อหนึ่งวัน ตั้งแต่วันนี้ถึง 365 วันข้างหน้า ตามเวลา Asia/Bangkok ราคาและรายละเอียดล็อกบันทึกไว้เมื่อพักล็อก การเปลี่ยนราคาในภายหลังไม่เปลี่ยนยอดของรายการเดิม
- กดยืนยันก่อนหมดเวลาเพื่อเข้าสู่สถานะ **รอชำระเงิน** อีก 30 นาที เปิด QR และส่งสลิปก่อนหมดเวลา เมื่อครบกำหนดโดยยังไม่ส่งสลิป รายการหมดอายุและคืนล็อกอัตโนมัติ
- ดูรายละเอียด เวลาที่เหลือ และประวัติที่ /bookings ลูกค้าเห็นเฉพาะรายการตนเอง และยกเลิกการพักล็อก/รายการรอชำระเงินได้โดยระบุเหตุผล
- ผู้จัดการและเจ้าของใช้เมนู **รายการจอง** และ **พักล็อก** ใน /admin เพื่อกรองตามวัน ตลาด และสถานะ ยกเลิกรายการหรือคืนล็อกพร้อมเหตุผล ประวัติที่หมดอายุหรือยกเลิกไม่ถูกลบ
- หน้ารายการดึงสถานะทุก 5 วินาที ผังทุก 15 วินาที เวลานับถอยหลังในหน้าเว็บเป็นข้อมูลประกอบ การตัดสินว่าหมดอายุและสิทธิ์ในการทำรายการใช้เวลาของ backend

| Booking API | สิทธิ์ / พฤติกรรม |
| --- | --- |
| POST /api/bookings/holds | ผู้เข้าสู่ระบบ ส่ง { stallId, date } พักหนึ่งล็อก 10 นาที |
| GET /api/bookings/me | ประวัติตนเอง กรอง status/date/market และแบ่งหน้า page/limit |
| GET /api/bookings/:id | รายละเอียดตนเอง บัญชีอื่นได้รับ 404 |
| POST /api/bookings/:id/confirm | ส่ง {} ยืนยันรายการตนเองเป็น pending_payment |
| POST /api/bookings/:id/cancel | ส่ง { reason } ยกเลิกรายการตนเองที่ held/pending_payment |
| GET /api/admin/bookings | manager/owner อ่านรายการทั้งหมดพร้อมข้อมูลติดต่อลูกค้า |
| POST /api/admin/bookings/:id/cancel | manager/owner ยกเลิกรายการพร้อม { reason } |
| GET /api/admin/holds | manager/owner อ่านรายการพักล็อกที่ยังไม่หมดอายุ |
| POST /api/admin/holds/:id/release | manager/owner คืนเฉพาะล็อกที่ยังอยู่ในสถานะ held พร้อม { reason } |

Unique partial index ใน MongoDB ให้มีรายการที่ใช้งานอยู่ได้เพียงหนึ่งรายการต่อล็อก/วัน การส่งคำขอพักซ้ำด้วยบัญชีเดิมคืนรายการเดิมโดยไม่ต่อเวลา การยืนยันซ้ำไม่ต่อเวลาชำระเงิน คำขอที่ขัดกับสถานะปัจจุบันได้ 409 และไม่เปลี่ยนรายการของผู้จองรายถัดไป

## PromptPay และตรวจสลิป (Phase 4)

ตั้งค่า `PROMPTPAY_ID` และ `PROMPTPAY_NAME` ใน backend/.env แล้ว restart backend ใช้หมายเลขมือถือไทย 10 หลักขึ้นต้น 0 หรือเลขประชาชน/ภาษี 13 หลักที่ผูกพร้อมเพย์ไว้จริง และชื่อบัญชีผู้รับจริง ค่าเริ่มต้นเป็นค่าว่าง: ระบบจะไม่สร้าง QR จนกว่าตั้งค่าครบ ไม่ใส่บัญชีรับเงินสมมติใน seed หรือ environment ของผู้ใช้

QR ใช้ `promptpay-qr` และ `qrcode` อิง [Thai QR Payment Standard ของ ธปท.](https://www.bot.or.th/content/dam/bot/documents/th/our-roles/payment-systems/about-payment-systems/ThaiQRCode_Payment_Standard.pdf) และ [เอกสารไลบรารีผู้พัฒนา](https://github.com/dtinth/promptpay-qr) ระบุยอดเงินบาทจากราคาที่บันทึกตอนพักล็อก บัญชีรับเงินถูกบันทึกเมื่อเปิด QR ครั้งแรก การแก้ environment ไม่เปลี่ยนผู้รับของรายการที่เปิด QR ไปแล้ว ก่อนรับเงินจริง ผู้ดูแลต้องตรวจบัญชีและ QR กับแอปธนาคารของตนเอง ราคาที่เป็นศูนย์ไม่รับผ่าน QR ให้ติดต่อผู้จัดการ

1. ลูกค้าเปิดรายละเอียดรายการ **รอชำระเงิน** แล้วกด **แสดง QR ชำระเงิน** ตรวจชื่อบัญชีและยอดที่แอปธนาคารแสดงก่อนโอน บันทึกภาพ QR ได้
2. ส่งภาพ PNG/JPEG ไม่เกิน 5 MB พร้อมยอดที่โอน วัน/เวลาโอน และเลขอ้างอิงภาษาอังกฤษ/ตัวเลข/ขีดกลาง สลิปต้องส่งก่อนหมดเวลา ภาพ PDF, SVG, ภาพเสียหาย และภาพเกิน 20 ล้านพิกเซลไม่รับ
3. เมื่อส่งสำเร็จเป็น **รอตรวจสอบสลิป** ล็อกยังสงวนไว้และไม่หมดอายุอัตโนมัติระหว่างตรวจ ลูกค้ายังไม่ได้รับการยืนยันว่ารับเงินแล้ว และยกเลิกเองไม่ได้ในสถานะนี้
4. ผู้จัดการ/เจ้าของเปิด /admin → **ตรวจชำระเงิน** ดูภาพและข้อมูล ตรวจเงินเข้าบัญชีจริงกับธนาคาร แล้วระบุเลขอ้างอิงที่ตรวจพบและยืนยันรับเงิน ระบบไม่มีบริการตรวจสลิปหรือข้อมูลธนาคารอัตโนมัติ
5. หากหลักฐานไม่ผ่าน ให้ระบุเหตุผลเพื่อปฏิเสธ ลูกค้าได้เวลา 30 นาทีเพื่อแก้ไข/ส่งใหม่ ประวัติทุกครั้งเก็บไว้ สูงสุด 10 ครั้งต่อรายการ **หากโอนแล้วอย่าโอนซ้ำ** ให้แก้หลักฐานหรือติดต่อผู้จัดการ
6. รับชำระแล้วเป็น **ยืนยันแล้ว** เลขอ้างอิงที่รับชำระและภาพสลิปเดียวกันไม่สามารถนำไปยืนยันรายการอื่นได้ แม้รายการเดิมยกเลิกแล้ว
7. ผู้จัดการยกเลิกรายการที่รับชำระแล้วได้พร้อมเหตุผล ระบบคืนพื้นที่และสร้าง **รอคืนเงิน** ผู้จัดการต้องโอนคืนเงินจริงเอง แล้วบันทึกเลขอ้างอิงการคืนเงิน ปุ่มบันทึกไม่ได้โอนเงินหรือเรียกธนาคาร ลูกค้าเห็นสถานะและเลขอ้างอิงคืนเงินในรายละเอียด

ภาพถูกอ่านและแปลงเป็น JPEG เพื่อตัด metadata/เนื้อหาส่วนเกิน ชื่อไฟล์ที่ส่งมาไม่ถูกใช้เป็นเส้นทางจัดเก็บ เก็บภาพใน MongoDB แยกเอกสารจากรายการจอง อ่านได้เฉพาะเจ้าของรายการและ manager/owner ผ่าน session ไม่มี URL สาธารณะ และส่ง private/no-store/nosniff สำรองฐานข้อมูลจึงครอบคลุมภาพสลิปด้วย จำกัดส่งสลิป 30 ครั้งต่อ 15 นาทีต่อ IP ที่ backend เห็น

| Payment API | สิทธิ์ / พฤติกรรม |
| --- | --- |
| POST /api/bookings/:id/payment/qr | เจ้าของรายการ ส่ง {} สร้าง QR ของ pending_payment ไม่ต่อเวลา |
| POST /api/bookings/:id/payment/slip | เจ้าของรายการ ส่ง multipart: slip, amount, transferredAt (ISO พร้อม timezone), reference |
| GET /api/bookings/:id/payment/slips/:slipId | เจ้าของรายการ หรือ manager/owner อ่านภาพ JPEG ส่วนตัว |
| POST /api/admin/bookings/:id/payment/review | manager/owner ส่ง { decision: approve, attemptId, verifiedReference } หรือ { decision: reject, attemptId, reason } |
| POST /api/admin/bookings/:id/payment/refund | manager/owner บันทึกการคืนเงินจริงด้วย { reference } เรียกซ้ำเลขเดิมได้ |

คำขอ POST ทั้งหมดต้องมี Origin ที่ตรง APP_ORIGIN เอกสาร Swagger ระบุ 400/401/403/404/409/413/429/503 ตามพฤติกรรม สถานะการรับชำระกับหลักฐานและการจองแก้ในเอกสารเดียวแบบ atomic ป้องกันการตรวจสลิปเก่าทับสลิปใหม่และอนุมัติซ้ำพร้อมกัน
